## Путь решения в DLL (тип 24, flag 0, studyflag 1 — как у EngineAdapter и algo_eval4)

```
identifyImageWrapper 0x18000b240 → identifyImage 0x18000d170
  getFeature 0x1800163d0 (identify-режим) → фичи пробы
  для кандидата: matcher 0x180028740(&ratio, probe, T, flag, studyflag, ctx, 0, 0)
      ratio > 0 → *pIdx = i, *pScore = ratio;  иначе *pIdx = −1, *pScore = ratio
  совпадение = rc == 0 && idx >= 0 && score > 0  (idx — номер кандидата, т.е. ratio > 0)
matcher 0x180028740: params = 0x18002f300(T, flag, studyflag); тип ∈ маске → 0x180028e70
```

`params` (0x18002f300): +0 = сдвиг порога от flag (0), +8 = 5, +0xc = 218, **+0x10/+0x14** — от
studyflag (0x180031e50: 0 → 0,0; 1 → 1,1; 2 → 1,0), +0x18..+0x2c = {23, 47, 40, 38, −1, 16}
(гейты соответствий и множители выбора), +0x30 = 137, +0x34 = 1, +0x3c = тип,
**+0x48 = probe+0x140 (packed_resolution)** (пишет matcher), +0x50 = flag.
Порог допуска = params+0 + 0xcf = **207**.

### Планировщик 0x180028e70

До цикла:
- ошибки: у пробы 0 минуций или coverage < 20, или пустой шаблон → 0x80000006;
- `continue` ([rbp−0x64], «идти дальше после совпадения») = params+0x10 (=1) и ctx+0x68c,
  но **0, если ((packed_resolution >> 8) & 7) ≥ 3** (0x180051820: значение + 4 ≥ 7);
- aux = вторичный класс разрешения пробы (0x180052210), cm = live_auxiliary[0] (0x180052310).

Цикл по записям шаблона в порядке T+0x87f0:
1. aux += класс записи (режим 2, максимум 5); при > 5 поздних отказов — однократный подъём aux и
   **сброс continue** (0x180029354); иначе при > 10 отказов — выход из цикла (0x18002935f).
2. Проход 1 (0x180028890): попытка 1 = обычные соответствия 0x180059030 + геометрия 0x18001f2f0
   → rec+0 = rec+4 = inliers; метрики 0x180050730 → selector/agreement/coverage, флаги формы
   0x180053740. **Попытка 2**, если agreement > 180 и inliers < 16: соответствия, направляемые
   преобразованием попытки 1 (0x180057ed0 → 0x18005ae30: окно 0x1500 в Q8, отступ 5 px, матрица
   дескрипторных расстояний попытки 1; выбор 0x180059e00 с множителями 40:36 при ≤ 10 inliers,
   иначе 40:38), новая геометрия. Её преобразование берётся, если selector > 128 и
   agreement − 4·(флаги +0x30,+0x34) выше; при большем числе inliers rec+4 = новое число и
   перекрытие 0x18005a160 считается по нему (для типа 24 прочие условия 0x180028db7..dee не
   действуют). При > 4 inliers и rec+0x28 < 30 перекрытие пересчитывается по попытке 1.
   Проход 2 (0x180024e10) → rec+8; rec+4 = max(rec+4, rec+8).
3. rec+4 ≤ 4 или rec+0x28 < 30 → пропуск (запись может пойти в fallback).
4. 0x18002bc90 (допустимость преобразования) → пропуск; метрики заново (0x180050730) по
   итоговому преобразованию: флаги +0x30 (масштаб вне 234..281), +0x34/+0x38 (|cos| между
   столбцами ≥ 0x147b / 0x28f6 в Q16), +0x64 угол 0..90°.
5. Префильтр 0x180023c10 — **до** вычисления study-метрик (+0x18..+0x20 ещё 0) → пропуск.
6. Оценка 0x180026ce0 → при слабой — уточнение 0x180052d20; оценка 0x1800258c0 (со штрафом за
   coverage) → status/conf/special; повторная оценка 0x1800535b0 (study-метрики) + 0x180019800
   (кроме случая conf == 2, aux ≤ 1, coverage ≥ 105…); special && rec+0x20 < 175 → status = conf = 0.
7. Поздний отказ 0x18002c4a0 → пропуск; study-фильтр 0x180024820.
8. **Допуск** (0x180029a9e): status == 1 или (selector > 207 и agreement > 195). Допущенная
   запись: count++, sum += (rec+4·256 + 15)/31, обновление «лучшей» записи (agreement, затем
   rec+4, затем coverage; при ctx+0x688/0x684 — с приоритетом conf/status).
   ctx+0x684 |= status, ctx+0x688 |= conf — и для недопущенных.
   **ratio = sum·100/count >> 8 пишется только при status == 1**; при continue == 0 после
   этого — выход из цикла.

После цикла (0x180029fb1..0x18002a4d8):
- continue == 0 → ctx+0x688 = 0; cm ≥ 6 и нет ctx+0x688 → ratio = 0;
- ratio ≠ 0 → результат;
- ratio == 0 и (aux ≥ 4 или cm ≥ 2) → 0;
- есть допущенные и packed_resolution == 0 → проверка лучшей записи 0x180027fb0 (сумма
  qualities ≤ 170, geometry% ≥ 10, пороги на agreement + metric20 с штрафом 3·флаги:
  425 / 400 / 415) → ratio = среднее всех допущенных;
- иначе fallback 0x180026f40 (на наших данных всегда ≤ 0: −1/−4/−7);
- ratio < 1 и кэш шаблона (T+0x8e10) → «второй шанс» 0x180027340 (у свежераспакованного шаблона нет).

Коды: 0 — проба ничего не набрала или отброшена правилами после цикла; −1/−4/−7 — биты причины
fallback (сумма геометрии < 6 → 4; max metric < 208 → 2; coverage < 128 → 1).

## Почему порт принимал чужих

`goodix_chicago_match_template_type24` порта (комментарий «+0x2a873 exits the gallery loop
immediately after the first admitted candidate») делал `add_geometry + break` на **первом
допущенном** кандидате независимо от status и возвращал положительный счёт. Допуск через
selector > 207 && agreement > 195 при status 0 — это ровно совпадения с `selected_index = −1`.
В DLL такой кандидат только входит в среднее; положительный ratio без status 1 возможен лишь
через 0x180027fb0 при packed_resolution == 0. Пример (genuine 2, INJECT): DLL допустила запись 5
со status 0, ratio не записан, после цикла cm = 1, aux = 2 → fallback → −1; порт вернул 19.
Кроме того, порт считал rec+4 = rec+0 (нет второй попытки геометрии), не заполнял флаги формы и
брал selector/agreement только по первой паре карт — счёт и status у него ниже, поэтому после
исправления одной лишь логики он отвергал часть своих (v1: TAR natural 7/17 против 11/17 у DLL).
Fallback порта (`aggregation.fallback_score`) никогда не заполняется, т.е. положительного счёта
не даёт — как и DLL на наших данных.

## Правки (`tools/algo/port_match_fixes.patch`, только goodix-chicago-match.c)

1. Логика решения `goodix_chicago_match_template_type24` — как в разделе выше: continue по
   packed_resolution и подъёму aux, выход при > 10 отказах, пропуск rec+4 ≤ 4 / matched% < 30,
   ratio только на status 1, ctx+0x684/0x688, лучшая запись и 0x180027fb0, правила после цикла,
   набор записей для fallback как в DLL (0x180029edc), selected_index = запись с наибольшим rec+4
   среди status 1.
2. Флаги формы преобразования 0x180053740 (+0x30/+0x34/+0x38, угол +0x64) — в порте не
   заполнялись (штраф в оценке и в 0x180027fb0).
3. Вторая попытка геометрии прохода 1 (0x180057ed0/0x18005ae30): у порта её не было. В DLL
   rec+4 > rec+0 у 66 из 92 кандидатов с rec+4 > 4.
4. selector/agreement 0x180050730 по второй паре карт (`secondary`): больший agreement берётся
   при selector1 > 220, больший selector — при agreement2 > 195.
5. Префильтр получает запись с нулевыми study-метриками; special && metric20 < 175 гасит флаги.
6. `MTRACE=1` — трасса по записям в stderr (формат как у `dll_match_trace.py`).

## Замечание по port_eval.sh

Раньше пересборка шла только при отсутствии бинарника или новом `port_eval.c`, и после смены
патча бинарник другой комбинации (FIXES/MFIXES) оставался старым. Теперь бинарник
пересобирается, если патченная копия (`.port-fixes/`, `.port-mfixes/`) новее него.
