# Стадия 1: препроцессор openchicago против AlgoChicago.dll

Цель: побайтное совпадение `preprocessor()` (профиль 12) по dst (8 бит), qcov {coverage, quality},
rc, контексту cbuf[0..5] и адаптивному состоянию на последовательности кадров от холодного старта.

## Как запустить

```sh
openchicago/tests/run.sh              # сборка оракула и теста, сценарии A и B; код выхода != 0 при расхождении
VERBOSE=1 openchicago/tests/run.sh    # строка на каждый кадр
```

- Оракул `tools/algo/oracle_pp.c` гоняет DLL (через `winpe.c`) и пишет дамп: на кадр
  `{seq, rec, purpose, rc, coverage, quality, framenum, multiplier_count}`, dst[5120] и планы
  kr (G+4), gain (0x1801144b0), multiplier (0x18010ab90), auxiliary (0x18011ddd0), cbuf[0..15]
  (формат 2; cbuf перед вызовом обнуляется, как у algo_eval4). `TRACE_RES=<файл>` дополнительно
  пишет входы/выходы 0x180038380 и его стадий (отладка контекста, run.sh не использует).
- Сценарий A: все 155 записей по индексу, purpose 0. Сценарий B: первые 12 natural с purpose 1,
  затем остальные по индексу с purpose 0. Оба: `ppp_param_init(12)` → `preprocess_init_calidata()` →
  `preprocessor_init(фон nat[0])`. Один сценарий на процесс (у DLL статическое состояние).
- Тест `openchicago/tests/test_preprocess.c` повторяет сценарий нашим кодом и печатает первый
  расходящийся кадр/пиксель/поле; cbuf[0..5] сравнивается на каждом вызове.
- `openchicago/tests/test_context_fuzz.c` (тоже из run.sh, ~3 с): контекст против внутренних функций
  DLL на возмущённых кадрах датасета и синтетических планах — ветки, которых нет в датасете
  (флаг hold, код 9 / rc 0xc351, уровни 0x180039240, второй лоб 0x18003def0, области истории
  0x18003fff0, состояния 3/4). 3000 вызовов 0x180043c70 целиком + по 1000 на помощники.

## Код

`openchicago/src/goodix-chicago-{preprocess,calibration}.{c,h}` — копия порта MR !648
(LGPL-2.1+, © Berke Kabagöz), изменения помечены адресами DLL. Новый вход:
`goodix_chicago_preprocessor_process(pp, raw, purpose, dst, &quality, &coverage)` → rc,
состояние — `goodix_chicago_preprocessor_get_state()`. Контекст cbuf[0..5]:
`goodix_chicago_preprocessor_process_context(…, hold, …, context)` (hold = 7-й аргумент DLL равен 1)
или `goodix_chicago_preprocessor_get_context()` после любого вызова.

## Статус

**Готово: оба сценария 155/155 вызовов бит-в-бит** — dst, coverage, quality, rc, cbuf[0..5] и
состояние (framenum, kr, gain, multiplier, auxiliary, счётчик множителя; история контекста сверена
отдельно дампом TRACE_RES — 155/155 в A и B). В датасете встречаются rc 0 и
0x7531 (13/12 кадров), кадры с re-run, откатом kr, пустые кадры, выбор альтернативного кандидата,
purpose 1.

Исправлено относительно порта (адреса — наша AlgoChicago.dll; у порта другая сборка, для этой
области его адреса = наши + 0x9b0):

1. Выбор усиления 0x18004ce60: при первом вызове процесса gain/multiplier/auxiliary = 0x2000; при
   framenum 0 kr = 0 и счётчик множителя = 0; при framenum ≤ 3 gain = 0x2000 (порт хранил
   нормированный gain всегда, правка из patch подменяла его только при использовании).
2. kr_update 0x180048fe0: нормировка gain только при framenum > 3 и mean ≠ 0, затем сглаживание
   при framenum ≤ 200. Гауссово ядро 0x18004edf0 считается в фиксированной точке через exp
   0x180056cd0/0x180056d10 (сдвиги по таблице логарифмов), а не через `exp()` — у порта
   расходилось на 1 при малых framenum.
3. Множитель 0x18004af10: `(m·n + r + (n+1)/2)/(n+1)`, n = счётчик до инкремента, затем
   n = min(n+1, 30). Отношение r усечено до u16. (У порта `/n`, у patch `(m·(n−1)+…)/n` — обе неверны.)
   Параллельно так же обновляется второй план auxiliary (без gain, копия счётчика).
4. Применение множителя 0x180049650: если не (счётчик < 5 и framenum > 3) и purpose ≠ 2
   (порт: только при счётчике > 5 или на самом первом кадре).
5. Гейт обновлений 0x180049650: множители и kr обновляются, только если > 205/256 пикселей имеют
   сигнал max(b−cur,0) > 100 (0x18004ae40) и кадр не «повтор» (0x180049270: средний |Δ| по
   сетке 40×32 с опорным кадром < 15 более 10 раз подряд останавливает обновления).
6. Откат 0x180044000 в конце кадра: если выход почти равен выходу прошлого кадра (минимум по сдвигам
   ±2 среднего |Δ| в окне 70×54 < 50) и framenum > 1 — kr и framenum возвращаются к значениям до
   кадра; gain/multiplier/auxiliary не откатываются.
7. Пиксели с kr = 0 берутся без нормировки (хвост 0x18004a950).
8. Quality 0x18000f870/0x18000f680: к базовому качеству порта добавлены штраф 0x18000fb70
   (при q < 70: доля пикселей «метка 4» кольцевого классификатора 0x180010200 в окнах с
   когерентностью не выше медианы, разметка 0x18000fca0; если < 35 % — q·(p/35)²) и поправка
   маски: если доля маски − coverage > 0x3333 (Q16), q = cov·q/mask·cov/mask; coverage ≤ 5 → q = 0.

9. Политика кадра 0x1800463e0 (в порте её нет; все 0x7531 датасета идут отсюда, путь порта
   0x180047ec0 на датасете ни разу не срабатывает):
   - план P = сигнал, нормированный только auxiliary (второй выход 0x18004a950); если выбран
     альтернативный кандидат (флаг G+0x26484 = 1, ставит 0x180046aa0), P дополнительно
     детрендируется по столбцам (0x180047710 / 0x180047ba0, как для альтернативного кандидата);
   - score1 = 0x1800456a0: доля маски (%); если в маске > 30 % пикселей без контраста в
     растянутом кандидате (0x180045d40: центрирование+сглаживание, растяжение между 5-м и 85-м
     перцентилем) по P (0x180050000, порог 80) и качество этой области
     (0x1800100f0: база + штраф/бонус 15 по «метке 4», порог 20) < 15 — «регион» = эта область,
     score1 = её доля;
   - score2 = 0x18005e3b0: средний |выход − 0x180043480(P)| (локальный контраст без
     центрирования) по региону (иначе по карте контраста первичного кандидата 0x180050000, порог 100);
   - кадр плохой, если score2 > 56 (purpose 1 и framenum < 100: 64). Тогда: при framenum < 100 и
     score1 > 90 — повторный прогон нормировки 0x18004a950 с временным framenum = 5 (второе
     обновление kr с весом 5, множителя, сглаживание gain при framenum 6); при score1 > 40 — rc 0x7531
     и код 2, иначе код 4 и rc 0;
   - 0x180054270: метка в младших битах первой строки (чередование 0/1 в столбцах 0..71, код в
     столбцах 72,73,75,76,77; при регионе — бит 74 и LSB всех пикселей ниже первой строки).
   - путь порта 0x180047ec0 (q < 35) теперь только при коде 0 и ставит код 1.
10. Альтернативный кандидат 0x180045af0: при покрытии маски ≤ 95 % (поле +0xe буфера маски)
    среднее по столбцу берётся только по пикселям маски, вне маски — 5000 (порт всегда брал все
    пиксели столбца).
11. Порог «плоского» пикселя в статистике 0x180043050 для mode 24 — 50, а не 150 (150 только для
    режимов из маски 0x2473800). Влияет лишь на путь 0x180047ec0.

12. Контекст cbuf[0..5] 0x180043c70 (после политики кадра, до разметки 0x180054270):
    `{состояние, флаг hold (0/2), счётчик, код класса, (маска·100+50)/N, 0}`, rc 0xc351
    (`GOODIX_CHICAGO_PREPROCESS_STATUS_CLASS_REJECT`, код 9) заменяет итоговый rc (0x1800489ad).
    Внутри 0x180038380 (вход через хвостовой переход 0x180038e20):
    - маска захвата эродируется на 6 пикселей маски с каждого конца строк и столбцов (0x180037b60),
      план `max(0, base − cur + 7095)` (0x180037cf0);
    - история (не при hold): при пустой и framenum > 1 — копия kr, счётчик min(framenum, 21);
      иначе 0x18003a610: при доле маски выше адаптивного порога (60…85, 0x180092350/54) — скользящее
      среднее `3·(план − 4095)`, нормированного на среднее (Q13), и счётчики присутствия ≤ 50;
    - классификатор 0x18003eb10 = разметка порта + 0x18003f8a0 (состояние 3/4 по связным группам
      вторичного плана выше порога) + 0x180037df0 (счётчики «остатка» по отфильтрованному градиенту,
      который DLL оставляет во входном плане; три крупнейшие группы > 75 пикселей → класс 3);
    - при счётчике истории > 20 — 0x18003b5b0: порог по гистограмме истории (0x18003bb40 +
      0x180042030), второй лоб (0x18003def0 → счётчик), спуск/обход (0x1800370a0, 0x18003e930,
      0x180040150), области (0x18003fff0 + рост 0x1800405b0 → класс 3; 0x18003cd60 → уровень);
    - класс 3 для cur < 50 во внутренней области; уровень «дыр» 0x180039240/0x18003fe90;
    - 0x180044ee0 (классификация порта) и сборка кода/состояния; при hold — максимум с
      сохранёнными (0x1800eb9c0/c4).
    Состояние (глобалы DLL 0x1800d8760…0x1800eb9c4, 0x180092350/54) хранится в объекте препроцессора.
13. Пиковое состояние анализа вторичного плана 0x1800394c0: лепестки ищутся по сглаженной
    гистограмме, отношение берётся по оконным суммам (у порта — всё по оконным суммам; кадр 9
    датасета давал 1 вместо 0).

Что осталось / не проверено датасетом:

- История контекста сохраняется DLL в calidata G+0x26488 (0x180036840) и читается на первом кадре
  (0x180036e50, при совпадении магии); у нас не сохраняется — старт всегда с пустой истории.
- Не покрыты датасетом, реализованы по дизасму: rc 0x29aa (плохой вход), срабатывание 0x180047ec0,
  purpose 2, 7-й аргумент `preprocessor` ≠ 0 вне контекста (флаг G+0x26484 = 2 у нас влияет только
  на контекст), старт с загруженной калибровкой (framenum > 3 на
  первом кадре; gain выводится из kr один раз), framenum ≥ 100 с re-run.
- Состояние вне calidata (gain, multiplier, auxiliary, счётчики, опорный кадр повторов, прошлый
  выход) в DLL живёт до выгрузки DLL; у нас — в объекте препроцессора. Сохранение/загрузка
  calidata (kr + framenum) — через существующий `goodix-chicago-calibration`, сверка save/load с DLL
  не делалась.
- Отладка: `TRACE=1` в `oracle_pp` (хуки внутренних функций DLL с трамплинами) печатает оценки
  политики кадра и повторные прогоны; `TRACE_PLANES` / `TRACE_STRETCH` сбрасывают входы/выходы
  0x180043050 / 0x180045d40.
