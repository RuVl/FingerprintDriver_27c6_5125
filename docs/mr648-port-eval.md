# Сверка открытого порта ChicagoHS (libfprint MR !648) с AlgoChicago.dll

Офлайн, без железа, на `tools/algo/frames_raw.bin` + `bg_raw.bin` (155 записей:
natural 30, genuine 25, impostor 100). Эталон — `algo_eval4` (оригинальная DLL через PE-загрузчик).

## Как собрать и запустить

```sh
cd tools/algo
./port_eval.sh 12                          # сборка (cc + glib/gio) и прогон, N=12
WARM=1 WARMSET=impostor ./port_eval.sh 12  # с прогревом kr на чужих пальцах, как в algo_eval4
FIXES=1 ./port_eval.sh 12                  # то же с port_preprocess_fixes.patch (см. ниже)
ENROLL=driver ./port_eval.sh               # политика регистрации EngineAdapter (tip/defer), как в драйвере
VERBOSE=1 ...                              # построчно по пробам

# побайтная сверка препроцессора (одинаковый протокол → одинаковая последовательность кадров)
DUMP_PROC=/tmp/dll.bin  ALGO=chicago ./algo_eval4 12
DUMP_PROC=/tmp/port.bin ./port_eval.sh 12
../../.venv/bin/python cmp_proc.py /tmp/dll.bin /tmp/port.bin [--all]

# только признаки и матчер порта на 8-битных картинках DLL
INJECT_PROC=/tmp/dll.bin ./port_eval.sh 12
```

- `port_eval.c` компилирует `upstream/.../goodix5125/chicago/*.c`, `common/goodix-crc.c`,
  `goodix5125-calib.c`, `goodix5125-proto.c` как есть. Заглушки libfprint не понадобились:
  бэкенд зависит только от glib/gio. Картинка после препроцессора перехватывается через
  `-Wl,--wrap=goodix_chicago_preprocessor_build_enhanced_checked`: препроцессор хранит
  состояние, поэтому вызывать его второй раз нельзя. `upstream/` не изменялся. `FIXES=1`
  патчит копию в `tools/algo/.port-fixes/`.
- В `algo_eval4.c` добавлена только опция `DUMP_PROC=<файл>`: на каждый вызов `preprocessor()`
  пишется `{rec, rc, quality, coverage}` и 5120 байт dst.
- Протокол совпадает с `algo_eval4` (калибровка, порядок кадров, галерея из первых N пригодных
  natural, свежая распаковка галереи на каждую пробу, `WARM`/`WARMSET`). Совпадением считается
  `score > 0`. Так решает `match_decide` в драйвере; у DLL `score>0 ⇔ idx>=0`, потому что её
  `idx` — номер шаблона-кандидата. `selected_index` порта — это номер подшаблона для
  templateStudy, он равен −1 на fallback-пути, и в критерии он не участвует.

## Вход, калибровка, OTP

- `raw[GOODIX_CHICAGO_PIXELS]` — 64 строки × 80 столбцов row-major. В README это названо
  «80 x 64» в смысле ширина × высота. Это транспонирование нашего буфера 80×64 из
  `goodix5125_image_decode_transposed` (`dst[(i%64)*80 + i/64]`). Раскладка та же, что после
  `transpose16` в `algo_eval4`, и совпадает с вендорской.
- Калибровка драйвера MR648 при холодном старте (`ensure_chicago_calibration`) — это
  `calibration_generate(ImageBase)`: gain = 0x2000 (Q13, единица), offset = ImageBase, framenum = 0.
  Затем идёт `preprocessor_new(cal, ImageBase)`. Это точный аналог DLL
  `preprocess_init_calidata()` + `preprocessor_init(bg)`, так что вариант «как драйвер» и вариант
  «как algo_eval4» совпадают. ImageBase берётся из bg записи nat[0].
- **OTP в алгоритм не идёт.** Порт берёт из него только `sensor_id` = OTP[0:16], и тот служит лишь
  привязкой print_data и файла калибровки. Реальный OTP взят из `dumps/probe-*.json`,
  `goodix5125_otp_parse` его принимает (tcode 0x110, fdt_delta 0x1d, dac bd c0 be be). Скрипт
  читает OTP из dumps, в код он не зашит.
- **Обучение kr в порте есть** (`update_temporal_gain`: бегущее среднее, cap 400, сглаживание
  5×5 при 3 < n ≤ 200). Кроме него есть второй адаптивный множитель (`update_adaptive_multiplier`,
  cap 30). **Сохранения нет**: состояние живёт только в `GoodixChicagoPreprocessor`.
  `chicago-calibration.dat` пишется лишь при инициализации — сгенерированный или rebased
  (у rebased заменён только ImageBase), с framenum = 0. Поэтому на каждой холодной активации
  kr в драйвере начинается заново. DLL/EngineAdapter сохраняют kr в `goodix_calib.dat` (notes/80).

## Препроцессор: побайтная сверка (N=12, одна последовательность кадров, оба с нуля)

Доля совпавших пикселей 8-битного выхода. Считаются только вызовы, где кадр приняли обе стороны.

| вызовы (rec) | порт как есть: exact / \|d\|≤2 / max\|d\| (медиана) | порт + FIXES |
|---|---|---|
| 0 (nat 0) | **100 % / 100 % / 0** — бит-в-бит | 100 % / 100 % / 0 |
| 1–3 | 9.6 % / 14.7 % / 202 | 22.8 % / 49.4 % / 32 |
| 4–29 | 36.2 % / 75.9 % / 24 | **92.4 % / 99.9 % / 3** (max 7) |
| 30–52 | 15.6 % / 25.8 % / 183 | **88.6 % / 99.6 % / 3** (max 9) |
| 53–154 | 12.7 % / 18.6 % / 255 | 29.4 % / 58.6 % / 65 |
| все 139 | 18.2 % / 31.0 % / 246; corr 0.89 | 51.3 % / 73.2 % / 27; corr 0.99 |

Первые 10 вызовов порта как есть (rec 25–34): exact 100, 9.7, 9.4, 9.6, 93.4, 30.2, 22.8, 29.3,
24.9, 30.0 %; max|d| 0, 255, 183, 202, 1, 29, 61, 39, 44, 23. В режиме WARM порт как есть даёт
exact 15.4 %, порт + FIXES — 31.6 %.

Порт отбраковывает меньше кадров: 4 против 12 у DLL. DLL выдаёт `0x7531` (poor capture) на
кадрах, где у порта картинка уже другая.

### Откуда расхождения (всё в адаптивном состоянии; статическая часть совпадает бит-в-бит)

1. **Кадры 1–3.** В DLL при framenum ≤ limit (3 для mode 24) gain равен единице
   (0x18004ce60, notes/80). Порт сразу применяет `normalized_gain`, построенный по 1–3 кадрам,
   и пока без сглаживания. Правка: единичный gain при `temporal_sample_count <= 3`.
2. **Насыщение адаптивного множителя (по всей видимости, ошибка порта).** После 30 кадров
   `update_adaptive_multiplier` считает `(m·30 + r)/30` вместо `(m·29 + r)/30`, и множитель
   растёт примерно на r/30 за кадр. Расхождение резко начинается ровно с 30-го вызова.
   С правкой вызовы 30–52 снова почти бит-в-бит.
   Обе правки лежат в `tools/algo/port_preprocess_fixes.patch`; в upstream не вносились.
3. **Кадры 53 и далее.** Остаток расхождений начинается с первого пустого или плохого кадра
   (rec 53: q = 0, c = 0; rec 57: DLL отдаёт `0x7531`). Порт обновляет kr и множитель на
   **каждом** кадре. DLL, судя по notes/80 §2.6, обновляет их только после проверок покрытия,
   качества и однородности. Простое отсечение по quality это не лечит, точный гейт не разобран.
4. У вызовов 1–3 с FIXES остаётся расхождение до 32–81. Вероятно, это bootstrap адаптивного
   множителя на ранних кадрах; не разбиралось.

## Матчер

Режим `INJECT_PROC` подставляет в порт 8-битные картинки DLL, так что остаются только признаки
и матчер порта. N=12, без прогрева, по пробам:
- все 17 совпадений DLL порт тоже засчитывает. Счёт совпал в 3 случаях из 17, в остальных у
  порта он ниже или равен;
- сверх этого порт принимает 13 проб, которые DLL отвергла со счётом −4/−1/0: 5 natural,
  5 genuine и **3 impostor**. У всех счёт 9–25, почти все пришли через fallback-путь
  (`selected_index = −1`). У DLL на таких пробах счёт ≤ 0, и impostor она не принимает ни
  одного (0/85 и 0/82). Отсечь их порогом по счёту нельзя: у настоящих совпадений порт тоже
  даёт 12–25.

## Вывод

- **Порт MR648 на наших данных DLL не эквивалентен — ни побайтно, ни по качеству.** Статическая
  часть препроцессора совпадает: первый кадр бит-в-бит, а с двумя правками десятки кадров
  подряд совпадают на 90 % пикселей и больше при |d| ≤ 2. Адаптивная часть (kr / множитель)
  расходится.
- Порт как есть **хуже DLL** по natural (8/17 против 11/17; с прогревом 9/17 против 15/17) и
  **пропускает чужих** (1–2 impostor из ~90–97), тогда как у DLL 0 во всех режимах.
- Главная проблема — матчер: на тех же картинках, что у DLL, он мягче. Выше genuine-recall
  (16/17 и 11–19/25), но FAR 2–9 % против 0 %. Fallback-ветка агрегатора даёт положительный
  счёт там, где DLL отвечает ≤ 0.
- С FIXES препроцессор заметно ближе к DLL, и по FRR порт + FIXES даже лучше DLL
  (N=12 WARM: 16/17, 17/25, 0/97). Но FAR в других режимах остаётся 1–4 %, так что это следствие
  мягкого матчера, а не эквивалентности.
- Для драйвера: без доработки матчера (fallback / порог) порт как замену DLL брать нельзя из-за
  FAR. Кроме того, kr не сохраняется между сессиями.
