# POV / OneKey: кадр, снятый MCU по нажатию кнопки питания

Статический разбор `win-driver/gfusb.dll` (UMDF-драйвер 1.1.125.20, imagebase `0x180000000`) и
прошивки `win-driver/fw/GF_ST411SEC_APP_12512.bin` (Cortex-M4/STM32F4, база `0x08020000`, файл не
зашифрован). На сенсоре стоит `12508`, в файле `12512`: выводы по прошивке относятся к соседней
версии. Устройство не трогалось.

Уровни уверенности, как в `00-overview.md`: **ТОЧНО** (видно в дизассемблере), *вероятно*,
_гипотеза_.

## Инструменты

```

uv run python -m fwre.dump gfusb.dll all > gfusb.asm     # 127k строк, .pdata есть
```

## Как gfusb отправляет команды (ТОЧНО)

`0x180063734` → `UsbSendDataToDeviceLock 0x180064f70` → `UsbSendDataToDevice 0x18006424c`.
Аргументы: `(ctx, -, cmd0, cmd1, payload, len16, use_checksum, ack_timeout_ms, data_timeout_ms,
event_idx)`. Байт команды = `cmd0<<4 | cmd1<<1`; **если `ack_timeout == 0`, к нему добавляется
бит 0** (`0x1800643e2`: `or al, 1`): так драйвер просит MCU не слать ACK. Прошивка разбирает этот
бит (`0x8026d50`, поле `[2]` структуры `0x20004ccc`) и при нём ACK не посылает (`0x8027db4`).
`use_checksum=1` — обычная сумма `0xaa`, иначе байт `0x88`. Таймауты от 1 до 999 мс поднимаются
до 1000. При `event_idx = -1` ответ ждут не здесь, а в потоке приёма.

Все прямые вызовы с константами cmd0/cmd1 (скрипт по вызовам `0x180063734`):

| cmd | где | что |
|---|---|---|
| `0x00` NOP | `0x1800637bc` SendNopCmd | 4 нуля, без ACK, без суммы (`0x01 … 0x88`) |
| `0xae` (как `0xaf`) | `0x1800610d4` GetMcuState | см. ниже |
| `0xd0` (как `0xd1`) | `0x18001f054` TLSServerInit | `00 00`, без ACK |
| `0xd2` | `0x18001ed80` | `00 00`, ACK 200→1000 мс, ответ асинхронно |
| `0xd4` | `0x18001ef8c` | `00 00` (UnlockTlsForce и конец рукопожатия) |
| `0xd8` | `0x18001ed18` | `00 00`, «wait for PBA result» |
| `0xe6` | `0x18001ecb0` | `00 00`, «wait for PBA key» |
| `0xee` | `0x180062638` | «get ec bios log» |
| `0xac` | `0x180028c80` ChicagoHUSetMode, режим `0xa`/тип 6 | «Set PC State», см. п.5 |
| `0xd6` | **нет** | gfusb его не шлёт (см. п.2) |

Приём: `data_from_USB 0x1800660f8` смотрит тип пакета (старший полубайт флага: `0xa`, `0xb`,
`0xc`, `0xd`). Тип `0xb` (TLS) идёт в `process_tls_data 0x1800249e0`, после расшифровки открытый
текст уходит в `data_from_device 0x180066d48`. Остальные типы попадают туда же напрямую.
`data_from_device` разбирает `[cmd][len16][payload…][сумма]` и раскладывает по `cmd0`.

## 1. Последовательность при старте (InitThread `0x180016ec0`, вызывается из D0Entry)

ТОЧНО по порядку вызовов в `0x180016ec0`:

1. `_QucikCheckMCU 0x18002110c`:
   - `UnlockTlsForce 0x18001fb04`: NOP, затем **`0xd4 00 00`** («force unlock it»);
   - при необходимости версия прошивки `0xa8` (`GetEvkVersionWithRetry 0x180060e38`) или NOP;
   - `0x96` (SetDriverState) только при «DriverState:Install»;
   - **`GetMcuState 0x1800610d4`**: команда `0xae`, байт на шине **`0xaf`** (без ACK), payload
     5 байт: `55 tt tt 00 00`, где `tt` = LE16 `wSecond*1000 + wMilliseconds` из `GetLocalTime`
     (лог «mcu-state TIMESTAMP 0x%04x»). Ответ ждут до 1000 мс на событии 6 и копируют 0x20 байт.
     Прошивка payload не читает (обработчик `0x80273f2`), так что `55` от Linux тоже годится.
2. Если `isPOVImageValid` (бит 0 байта 1 ответа, `[rsp+0xe1]&1`), лог «ensure tls handshake will
   be done»: драйвер **принудительно делает новое TLS-рукопожатие**, даже если TLS «alive».
3. `_DeviceInit 0x180020df0`, если ещё не выполнялся.
4. **TLS-рукопожатие** `0x180021a20`: `0xd0` → записи TLS → `0xd4`.
5. Проверка конфигурации, при «Config data lost» загрузка `0x90` (`0x18006f270`); ключ и результат
   PBA (`0xe6`, `0xd8`); лог EC BIOS (`0xee`). Это зависит от PBA и от состояния.
6. **Только если POV valid** (`0x18001805f`):
   - `0x18001496c`: обнулить 5 буферов POV (`0x180556d50[0..4]`), индекс `0x18054ed48 = 0`;
   - `ResetEvent(ctx+0x1e0)`, затем **`0xd2 00 00`**;
   - «Init: wait for pov image...%dms»: `WaitForSingleObject(ctx+0x1e0, cfg+0x444)`, по умолчанию
     2000 мс;
   - `GetMoreOneKeyImg 0x180016bd0`: при `OneKeyBootRetrySwitch` (по умолчанию 1) для
     `i = 1 … OneKeyBootRetryMaxCnt-1` (по умолчанию 3): `0xae`, и пока бит POV стоит, снова
     `0xd2` и ожидание.
7. «update all base», затем при наличии ожидающего запроса WinBio «Init: Use POV data for pending
   request» (`0x180070368`, отдача кадра).

**Порядок: POV забирается после TLS-рукопожатия (ТОЧНО).** Прошивка это требует: обработчик
`0xd2` (`0x802d602`) при включённом TLS (`0x20000110 != 0`) отвечает только в состоянии TLS
`> 15` (соединение установлено), иначе тихо выходит.

**Шифрование (ТОЧНО по прошивке).** Ответ `0xd2` собирается в буфере POV и отправляется через
`0x803bd90(tls_ctx, buf+0x11, size+4)` (запись TLS), когда TLS включён. Без TLS он уходит пакетом
`0xc0` через `0x8026f04`. Обычный кадр `0x20` (`0x802b430`) отправляется так же. Значит, на 5125
POV-кадр приходит **TLS-записью (пакет типа `0xb`), как обычный кадр**. Драйвер оба пути сводит
в `data_from_device`.

**Формат ответа `0xd2` (ТОЧНО, прошивка `0x802d650…0x802d6d6` и драйвер `0x180067fbf…`)** —
открытый текст:

```
d2 | len16 = size+1 | aa | 4 байта заголовка SPI | 7680 байт кадра | 4 байта CRC | 88
```

- `size` берётся из `0x20006d48+0x30`, это та же длина, что у кадра `0x20`; драйвер проверяет
  ровно `0x1e04 = 7684` (ChicagoHU get_rawdata `0x18002d2e0`). Итого `len = 0x1e0a` и **7693 байта
  открытого текста, как у обычного кадра**.
- Первый байт полезной нагрузки — **маркер `0xaa`**. Прошивка ставит его после съёмки
  (`0x802d6bc`). Драйвер делит кадры по нему: ответ `0x20` с `0xaa` — «not process POV here», ответ
  `0xd2` без `0xaa` — «not to process non-POV here». У обычного кадра на этом месте первый сырой
  байт SPI (в дампах `5b/e8/f4/48`).
- Отдельного байта статуса или индекса в ответе нет. Индекс ведут обе стороны: в MCU
  `0x20000794`, у хоста `0x18054ed48` (лог «Get POV data, index:%d.»). Кадров в MCU —
  `0x20000111` (прошивка пишет туда 3, в одной ветке 1). Это **старший полубайт байта 2 ответа
  `0xae`** («captured_num:%d(%d)» = `b2>>4`, `b2&0xf`); младший полубайт — бегущий счётчик
  съёмок и выдач. У хоста 5 буферов (`InitOneKeyImgBuffer`), но Init делает не больше
  `OneKeyBootRetryMaxCnt` = 3 запросов.
- Каждый `0xd2` выдаёт следующий кадр, `idx++`. **После последнего (`idx == count`) прошивка
  сбрасывает `isPOVImageValid`** (`0x802d756`).

Раскладка ответа `0xae` (ТОЧНО: печать `0x1800626a8`, сборка в прошивке `0x80273f2`, структура
`0x20006d38`):

| байт | поле | источник в прошивке |
|---|---|---|
| 0 | version | |
| 1 | бит0 isPOVImageValid, бит1 isTlsConnected, **бит3** isLocked | `0x20000780==1`; состояние TLS `>15`; `0x2000078c` |
| 2 | `captured_num(%d)` = старший/младший полубайт | `0x20000111`<<4 \| счётчик |
| 5 | не печатается; см. п.7 | счётчик окон и биты 0x10/0x20/0x08 |
| 8 | \|= `0x2000059c` | |
| 9 | EC_Falling_Cnt | `0x20000772` |
| 10–11 | WakeupToPovTime, мс | `0x20000774`, +1 за тик SysTick |
| 12 | WakeupSrc | `0x20000776` (бит0 ставит обработчик EXTI0) |
| 13 | OneKeyProcedure | `0x20000777` |
| 14 | FdtTxFailUsbSuspend | `0x20000778` |

Важно: **isLocked — бит 3, а не бит 2**, как считает `decode_mcu_state()` в
`tools/goodix5125/goodix.py`. Бит 3 = `0x2000078c`: его ставит `0xd0` в режиме TLS, снимает
`0xd4`.

## 2. CRC кадра (ТОЧНО, проверено на дампах)

Команда `0xd6` не используется: в прошивке у `cmd0=0xd` есть только варианты
`cmd1 = 0 / 1 / 2` (`0xd0`, `0xd2`, `0xd4`, `0x802d5cc`), на `0xd6` ответа не будет. В gfusb есть
лишь ветка разбора ответа `cmd1=3` («---test pov image ready»), отправителя нет.
`pov_image_check()` в `goodix.py` на этой прошивке зависнет.

CRC считает хост, функция у POV и обычного кадра одна: указатель `ops+0x13d60` (`0x18056aae0`),
у ChicagoHU — `0x18002d2e0` → `0x180027ff4`:

- вход: `payload+5`, длина `len-6` = 7684 байта (кадр 7680 + 4 байта CRC);
- **CRC-32/MPEG-2**: полином `0x04C11DB7`, MSB-first, init `0xFFFFFFFF`, без отражения и без
  финального XOR (`0x18001510c` строит таблицу, `0x1800151b0` считает); берётся по первым
  7680 байтам;
- хранится в 4 последних байтах в порядке `b[n-2]<<24 | b[n-1]<<16 | b[n-4]<<8 | b[n-3]`
  (то есть два 16-битных числа big-endian, младшая половина первой).

Проверено на `dumps/capture-*/background.bin` (7693 байта, `d[8:8+7684]`): совпадает 4 из 4.
Это касается и обычных кадров; драйвер для Linux CRC сейчас не проверяет.

При ошибке CRC у POV: «pov crc check failed», событие всё равно взводится («Set oneKeyImageEvent
no matter CRC pass or not»), кадр не копируется. При успехе копия идёт в
`OneKeyImgBuffer[idx]`, затем `process_onekey_image 0x180072d6c`, затем `idx++`.

## 3. Очистка POV

**На хосте (ТОЧНО).** `ClearPOVImage 0x18006074c` снимает флаг «есть POV» (`0x18054ed44`) и
обнуляет буферы; **команд в MCU не шлёт.** Вызывается:
- по таймеру `gf_onekeyImage_valid_timer` (`0x18006fa94`, обработчик `0x1800622e0`);
- при UNLOCK или входе в сессию (`sessionThread 0x180012970`, «UNLOCK to clear pov data right away»);
- в `MilanEvtDeviceD0Exit 0x180018d30`.

`process_onekey_image` решает, оставить ли кадр (`ctx+0x1a8` = POWER_ACTION прошлого перехода:
2 = сон, 3 = гибернация; «Never» = в Windows «Требовать вход: никогда», `GetRequireSignIn`;
быстрый запуск = `HiberbootEnabled`):
- сон + «Never» → «wake from sleep with no sign-in, clear pov data», флаг 0;
- гибернация + «Never»: с быстрым запуском — флаг 1 и таймер на `TimeS4OnekeyimageValid`, без
  него — «drop», флаг 0;
- иначе флаг 1 и таймер на `TimeGeneralOnekeyimageValid`.

Но в этой сборке **таймер всегда ставится на 10 с**: `0x18006fbec mov [rsp+0xd8], 0xa` после лога
«timeout value %d to %d seconds»; `0x1800655ec` переводит секунды в −10⁷·с.

**В MCU** — п.7.

## 5. `0xac` — не «SET_POV_CONFIG», а «Set PC State» (ТОЧНО)

Отправка: `ChicagoHUSetMode 0x180028c80`, режим `0xa`, тип 6 (`0x180029a6b`, лог «Set PC State»).
Payload: `[state][00][FDT down base × state]`, длина `state*word(0x180541dd4)+2`. База берётся из
`0x18054b838` — тот же буфер, что уходит с FDT-командами (лог «down base sent:»). Отправка без ACK,
то есть на шине `0xad`.

Когда: `MilanEvtDeviceD0Exit` → `_NotifyPowerState(1)` (`0x180062298` → `0x180065e58` → действие
ACT_SET_PC_PWRSTATE). Только если целевое действие — сон или гибернация; при выключении и
перезагрузке «No Need Send PowerState to MCU».

**Для POV не нужна:** в прошивке у `cmd0=0xa` в таблице переходов `0x80271b8` пункт 6 ведёт на
выход (`0x8027536`), то есть `0xac` прошивка 12512 игнорирует. На железе POV снимается и после
выключения из Linux. _Гипотеза:_ в других прошивках так передаётся база FDT для обнаружения
касания при выключенном ПК.

## 6. Формат кадра POV по сравнению с `0x20` (ТОЧНО)

Те же 7693 байта открытого текста: `8 = [cmd][len16][5 байт заголовка]` + 7680 + `5 = CRC32(4) + 0x88`.
Отличия: байт команды `0xd2` и `0xaa` в первом байте заголовка. Распаковка 12 бит та же
(`0x1800282f8`, 0x1e00 байт).

Связанный факт (ТОЧНО по коду прошивки): обычная съёмка `0x20` (`0x802b430`) кладёт кадр в
`0x20006d8c[0]`, а это **слот 0 буферов POV**. Большие отправки (`> 0x1388` байт, `0x8026e48`)
используют `0x20006d8c[idx]` как рабочий буфер. *Вероятно*, съёмка `0x20` до выдачи POV затирает
POV-кадр: POV надо забирать до любой `0x20`.

## 7. Почему MCU сбрасывает флаг POV и что делает Windows

Флаг — `0x20000780` (1 = кадр есть). Места сброса в прошивке (ТОЧНО):

1. **USB suspend → STOP → resume.** Обработчик suspend в HAL PCD (`0x802c848`, GINTSTS.USBSUSP)
   ставит `0x2000079a = 1`. Главный цикл (`0x8029c52`) при ПК во включённом состоянии (PA5 = 1) и
   DSTS.SUSPSTS вызывает `0x8029224`: гасит тактирование PHY, разрешает EXTI18 (OTG wakeup) и
   входит в STOP (`0x8023370`). Обработчик resume (`0x802c8b8`, GINTSTS.WKUINT) пишет источник
   пробуждения `0x2000079d = 3`. После выхода из STOP: **если источник 2 или 3, `POV valid = 0`**
   (`0x8029348…0x8029364`; то же во втором маршруте сна `0x80294f4…0x8029510`). Источник 1 (EXTI0)
   и 4 (EXTI9_5) флаг не трогают.
2. **Таймаут 180 с.** Обработчик SysTick (`0x802c185` → `0x802113c` → `0x802bf10`) раз в 1000
   тиков (*вероятно*, 1 с при SysTick 1 кГц; WakeupToPovTime в мс считается в том же месте по
   тикам) увеличивает `0x20000788`, если `0x2000010f == 0` и POV valid. При значении `> 0xb3`
   флаг сбрасывается. `0x2000010f` обнуляет **любая команда `0xd?`** (`0x802d5c6`, в том числе
   `0xd4`, который Windows шлёт первым) и конец «окна пробуждения» при включённом ПК (`0x802b13a`).
3. **Конец окна при выключенном ПК.** `0x802b074`: после 5 «секундных» тиков окна проверяется PA5;
   если 0 (ПК не включился), то `b5 |= 0x20`, POV = 0, MCU уходит в сон (`0x80293a4`). Если PA5 = 1,
   то `b5 |= 0x10`, окно закрывается (`0x2000010f = 0`) и начинается отсчёт 180 с.
   Каждое окно увеличивает младшие биты `b5`. Отсюда **байт 5 ответа `0xae`**: младшие биты —
   число окон, 0x10 — «ПК был включён в конце окна», 0x20 — «ПК был выключен, POV сброшен»,
   0x08 — уровень входа в `0x802d7b6`. Биты накапливаются до сброса MCU.
4. PA5 = 0 при счётчике `0x20000790 > 7` (`0x8029cfc`) и `0x2000077c & 2 == 0` (`0x802bd04`) —
   варианты «ПК выключен».
5. Выдача последнего кадра через `0xd2` (п.1).

PA5 _гипотеза_: линия питания или S0 от EC (`ldr r0,=0x40020000; movs r1,#0x20`).

**Наблюдение в Linux** (`b5 0x21 → 0x33`, POV = 0 через 60–120 с) объясняется пп. 1–2. Байт `0x33`
= 3 окна + 0x10 + 0x20: окно закрылось при включённом ПК, значит пошёл отсчёт 180 с. 60–120 с
меньше 180, поэтому *вероятная причина* — п.1: Linux через 2 с перевёл устройство в runtime
suspend, MCU ушёл в STOP, а наш запрос `0xae` вызвал USB resume (источник 3), и флаг сбросился.
В UEFI USB не засыпает, поэтому флаг жил больше 30 с.

**Что делает Windows** (ТОЧНО по коду; выводы — вероятно):
- Специальной команды, удерживающей POV, нет. Кадр просто забирается сразу в InitThread из
  D0Entry, до первого простоя.
- Простой: `milanFusbCreateDevice 0x180023598` вызывает `WdfDeviceAssignS0IdleSettings` с
  IdleTimeout **10000 мс**. IdleCaps = **IdleUsbSelectiveSuspend** на системах с Modern Standby,
  `IdleCannotWakeFromS0` («can not wake from S0») на S3. В INF:
  `WinUsbPowerPolicyOwnershipDisabled=1` (политику питания ведёт gfusb), `DeviceIdleEnabled=1`,
  `DefaultIdleTimeout=5000`. Selective suspend в Windows есть, но наступает через 5–10 с после
  старта, а InitThread укладывается в TLS (~1 с) плюс до 3×2 с на `0xd2`.
- `0xd4` в начале (UnlockTlsForce) запускает 180-секундный отсчёт MCU, но кадр к тому времени уже
  забран.
- `FdtTxFailUsbSuspend` (`0x20000778`) прошивка увеличивает, если при USB suspend в очереди
  оставался неотправленный пакет FDT (`cmd0 == 3` или `0xda`), `0x8029ca6…`.

Выводы для Linux (_гипотеза_, не проверено): (а) не давать устройству засыпать до выдачи POV,
например udev `ATTR{power/control}="on"` для `27c6:5125`, или держать его открытым; (б) порядок
как в Windows: `0xae` → TLS (`0xd0`…`0xd4`) → `0xd2` × до 3 раз, перед каждым повтором
проверяя бит в `0xae`, и всё это до первой `0x20`; (в) проверять CRC-32/MPEG-2.
