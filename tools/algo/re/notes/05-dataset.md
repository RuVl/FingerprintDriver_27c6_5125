# Датасет: что у нас реально есть (для подачи в вендорский пайплайн)

Источник: `dumps/dataset/*.npz`, ключ `frames`, форма `(N, 4, 5120)` `uint16`.
- 5120 = 64×80 (W=64, H=80), значения ~350..3350 → **сырые 12-битные** отсчёты АЦП.
- 4 кадра на касание. Из `tools/tune/sigfm_eval.py`: индекс **0 = фон (base)**,
  индекс **2 = полный контакт (down)**. (Индексы 1,3 — промежуточные фазы касания.)
- Наш `process(bg, frame) = clip(bg − frame)` (ридж темнее) → 8-бит. Это НАШ
  препроцессинг, зеркало `process_frame()` в goodix5125.c. НЕ вендорский.

Наборы: genuine=25, natural=30, impostor(10)+impostor(100), с JSON-метаданными
(base/down hex + FDT masks).

## ВАЖНО для матчер-пути
Текущий `tools/algo/frames.bin` = **наш** 8-битный препроцессинг. Если вендорский
`preprocessor` ждёт сырьё — нужно экспортировать СЫРЫЕ кадры (idx 2) и, вероятно,
фон (idx 0) как калибровку, и прогнать их через вендорский `preprocessor`, а не
через наш `process()`. План: после подтверждения формата от агентов сделать
`export_raw.py` → `frames_raw.bin` (uint16, 64×80) + `bg_raw.bin`.

Гипотеза о двойной обработке: сейчас мы кормили `enrolAddImage` НАШИМИ 8-бит
кадрами при `ppp_param_init(3)` → он их принимал (rc=0), но признаки строились не
из вендорски-препроцессированных данных → сравнение неадекватно. См. [00-overview] F1/F2.
