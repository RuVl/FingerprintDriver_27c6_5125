# povprobe — состояние MCU до загрузки ОС

UEFI-программа: находит сенсор 27c6:5125 через `EFI_USB_IO_PROTOCOL` прошивки и
спрашивает у MCU состояние (`query_mcu_state`, 0xae), затем версию прошивки (0xa8).
Пока флаг POV стоит, опрос повторяется раз в 10 с до 5 мин (прервать — Esc), так видно, когда MCU сам сбросит кадр. Других команд нет: ни reset, ни flash, ни PSK.

Зачем: в Windows кнопка питания со сканером работает как «вход одним касанием».
По строкам `gfusb.dll`/`EngineAdapter.dll`: MCU сам снимает кадр в момент нажатия
(POV, «OneKey»), драйвер при старте видит `isPOVImageValid` в ответе 0xae, забирает кадр
(0xd2, проверка CRC) и отдаёт его первому запросу Windows Hello. Кадр живёт ограниченное
время (`TimeS4OnekeyimageValid`, `TimeGeneralOnekeyimageValid`). povprobe проверяет
первый шаг: есть ли такой кадр у MCU, когда ОС ещё не тронула сенсор.

Раскладка ответа взята из `decode_mcu_state()` в `tools/goodix5125/goodix.py` и частично
угадана; сырой ответ пишется всегда.

## Сборка

```sh
./build.sh   # clang + rust-lld из rustup, gnu-efi не нужен
```

## Запуск

Программа кладётся в ESP, подписывается ключом sbctl (Secure Boot) и запускается
одноразово через `BootNext`; после неё прошивка продолжает загрузку по `BootOrder` (GRUB).
Лог последнего запуска — в переменной NVRAM `PovprobeLog-cbdbd978-a794-476a-b8c2-8592c5b04f79`:

```sh
tail -c +5 /sys/firmware/efi/efivars/PovprobeLog-cbdbd978-a794-476a-b8c2-8592c5b04f79
```

Не в файл: при выходе из гибернации ESP остаётся смонтирован замороженным ядром,
и запись в него из прошивки ломает ядру картину FAT. Первая версия писала в
`\EFI\povprobe\povprobe.log` — после такой записи `/boot` нужно перемонтировать.

```sh
sudo install -Dm644 povprobe.efi /boot/EFI/povprobe/povprobe.efi
sudo sbctl sign /boot/EFI/povprobe/povprobe.efi
sudo efibootmgr --create-only --disk /dev/nvme0n1 --part 1 \
  --label povprobe --loader '\EFI\povprobe\povprobe.efi'   # запомнить номер BootXXXX
sudo efibootmgr --bootnext XXXX   # перед каждым опытом
```

Откат: `sudo efibootmgr --bootnum XXXX --delete-bootnum && sudo rm -r /boot/EFI/povprobe`,
переменная: `sudo chattr -i /sys/firmware/efi/efivars/PovprobeLog-* && sudo rm /sys/firmware/efi/efivars/PovprobeLog-*`.

## Результаты (2026-10-04, лог в `/boot/EFI/povprobe/povprobe.log`)

| Опыт | Ответ 0xae | POV | Прочее |
|---|---|---|---|
| A: выключение → кнопка пальцем | `01 03 35 00 00 21 00 00 20 03 13 00 11 b0 00 00` | **1** | captured 3(5), EC falling 3, wakeup→POV 19 мс, src `0x11`, onekey `0xb0` |
| B: выключение → кнопка ногтем | `01 02 30 00 00 32 00 00 20 04 00 00 10 14 00 00` | 0 | EC falling 4, src `0x10`, onekey `0x14` |
| C: гибернация (S4) → кнопка пальцем | `01 03 35 00 00 21 00 00 20 01 13 00 11 b0 00 00` | **1** | как в A; EC falling 1 (счёт с перезагрузки) |
| D: выключение → пальцем → GRUB, LUKS, вход; запрос из Linux (`tools/pov_state.py`) | `01 02 35 00 00 33 00 00 20 02 13 00 11 b0 00 00` | **0** | всё остальное как в A; через ~1–2 мин после нажатия, сенсор в USB autosuspend |
| E: выключение → пальцем, опрос в UEFI раз в 10 с | `01 03 35 00 00 21 …` → `01 02 35 00 00 21 …` | **1 → 0** | флаг сброшен между +170 и +180 с от первого запроса; байт 5 не изменился |
| перезагрузка (`reboot`) | `00 00 30 00 00 00 00 00 20 00 00 00 01 00 00 00` | 0 | всё обнулено, src `0x01` |

- MCU сам снимает кадр при нажатии кнопки, без участия ОС и без команды `0xac`
  от Windows: функция включена в прошивке сенсора.
- В S5 MCU остаётся под питанием: флаг TLS (1) сохраняется после сеанса Linux,
  счётчик нажатий (байт 9) растёт от включения к включению. Перезагрузка
  обесточивает сенсор и сбрасывает всё.
- Сам MCU кадр не сбрасывает: за 30 с опроса флаг не изменился. Срок
  действия задаёт драйвер (`TimeGeneralOnekeyimageValid` и т. п. в Windows).
- Байт 12 (`WakeupSrc`): бит 0 — палец при нажатии (`0x11`/`0x10`); `0x01` — после сброса.
- После гибернации (S4) — то же, что после выключения. Первая попытка гибернации
  откатилась («Wakeup event detected during hibernation, rolling back»): кнопку нажали
  до того, как ноутбук выключился (до выключения ~35 с, экран гаснет раньше).
- Лог опыта C версия 1 записала в ESP, смонтированный замороженным ядром; Linux потом
  вернул старый размер файла, текст нашёлся за концом файла в его последнем кластере.
- До Linux флаг не дожил (D), хотя кадр был снят. Опрос в UEFI (E) подтвердил разбор прошивки
  (`tools/algo/re/notes/90-pov-image.md`): MCU держит кадр ~180 с, без USB suspend. В D байт 5
  стал `0x33`, а в E остался `0x21`, и до запроса в D прошло меньше 180 с — скорее всего, флаг сбросил USB autosuspend Linux (2 с простоя),
  а не таймер. Для Linux нужно: запретить autosuspend сенсора и забрать кадр (0xae → TLS → 0xd2)
  в пределах ~3 мин после нажатия.

## Опыт F: кадр забран в Linux (2026-10-05, `tools/pov_fetch.py`)

С `udev/71-goodix-5125-pov.rules` (без autosuspend) и замаскированным fprintd: включение пальцем,
GRUB, LUKS, вход, затем `0xae → TLS → 0xd2 ×3`. Все три ответа — 7693 байта, команда `0xd2`,
маркер `0xaa`, CRC-32/MPEG-2 сходится; на кадрах видны гребни (`dumps/pov-fetch-20261005-104707/`).
Счётчик в байте 2 растёт с каждой выдачей (`35 → 36 → 37 → 38`), после третьей MCU сам снял флаг.
Байт 5 после TLS: `0x32 → 0x3a` (бит 3 — блокировка TLS).

## Драйвер: вход по нажатию (2026-10-05, локальная ветка `goodix5125-pov`, bcecb8a)

С `GOODIX5125_POWER_BUTTON_UNLOCK=1` (`packaging/fprintd/power-button-unlock.conf`) и
`udev/71-goodix-5125-pov.rules`: выключение → кнопка пальцем → LUKS → автологин →
`fprintd-verify` без касания → сразу `verify-match` (кадр 1/3, score 43, q=99, c=100).
Две ошибки по дороге: `0xd2` не было в белом списке `goodix5125-proto.c`; результат,
отданный синхронно внутри vfunc, клиенты fprintd отбрасывают (ответ на VerifyStart ещё не
пришёл) — теперь отчёт откладывается в главный цикл.
